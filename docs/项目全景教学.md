## 1. 先用一句话理解这个项目

`RAG-MCP` 是一个“本地知识库后端”。

它做的事情可以概括成这条链路：

1. 把本地文档读进来
2. 切成适合检索的小块
3. 把这些小块建立索引
4. 用户提问时先检索相关内容
5. 再把检索结果交给大模型生成答案
6. 同时把过程记录下来，方便追踪、评测和排障

这个仓库不是一个“只有模型调用”的脚本，而是一个完整的后端工程。它同时提供三种使用方式：

- REST API：给浏览器、前端、脚本、调试工具调用
- MCP stdio server：给支持 MCP 的 Agent / Host 调用
- Dashboard：给人直接查看运行状态和结果

## 2. 什么是 RAG

如果你完全没接触过 RAG，可以先记住这个定义：

`RAG = Retrieval-Augmented Generation`

中文可以理解成：

“先检索，再生成”

普通大模型回答问题时，通常只依赖它训练时学到的知识。  
RAG 的做法不同：它会先去你自己的知识库里找资料，再基于找到的资料回答。

这个项目里的 RAG 流程大致是：

1. 文档摄取
2. 文档切块
3. 为每个块生成向量
4. 把向量和文本一起存起来
5. 用户提问
6. 把问题也转成向量
7. 在知识库里找最相关的若干块
8. 把这些块拼成提示词
9. 调用大模型输出答案

这就是它为什么既有“向量库”，又有“Embedding Provider”，又有“LLM Provider”。

## 3. 什么是 FastAPI

`FastAPI` 是一个 Python Web 框架。

你可以把它理解成：

“负责把 HTTP 请求接进来，然后交给你的 Python 代码处理，再把结果返回出去”

比如浏览器访问：

```text
http://127.0.0.1:8000/api/v1/health
```

FastAPI 会把这个请求路由到对应的 Python 函数，然后把函数返回值变成 JSON 响应。

在这个项目里，FastAPI 主要负责这些事：

- 注册接口路由
- 接收和校验请求参数
- 调用应用层 Use Case
- 把 Use Case 的结果封装成统一响应格式

它不负责核心业务逻辑。  
核心业务逻辑在 `application/use_cases/`、`domain/services/` 和 `infrastructure/` 里。

## 6. 启动入口：FastAPI 是怎么被创建出来的

文件：
[backend/src/rag_mcp/main.py](/d:/PersonalProject/RAG-MCP/backend/src/rag_mcp/main.py:1)

这是整个 Web 服务的起点。

核心代码片段：

```python
def create_app() -> FastAPI:
    configure_logging()
    app = FastAPI(title="RAG MCP", version="0.1.0")
    app.include_router(api_router)
    return app
```

这个片段做了三件事：

1. 调用 `configure_logging()` 配置日志
2. 创建一个 `FastAPI` 应用对象

可以把 `FastAPI()` 想成“创建整个网站后端对象”，  
而 `include_router(api_router)` 的意思是“把所有接口路由挂上去”。

如果服务能启动，通常就说明这个文件没有问题。

## 7. REST API 是怎么定义的

文件：
[backend/src/rag_mcp/api/v1/routes.py](/d:/PersonalProject/RAG-MCP/backend/src/rag_mcp/api/v1/routes.py:1)

这是 HTTP 接口的集中定义处。

### 7.1 路由对象

```python
router = APIRouter(prefix="/api/v1")
```

这里的意思是：

- 这个文件里注册的所有接口
- 都会自动带上 `/api/v1` 前缀

所以函数上写 `@router.get("/health")`，最终接口就是：

```text
/api/v1/health
```

### 7.2 一个最简单的接口

```python
@router.get("/health")
def health() -> dict:
    return {"code": 0, "message": "ok", "data": {"status": "healthy"}, "trace_id": None}
```

它的功能非常简单：

- 不读数据库
- 不读配置
- 不走业务逻辑
- 直接返回“我活着”

所以当你怀疑服务有没有启动成功时，这个接口是最先该测的。

### 7.3 业务接口的基本形态

再看一个真正有业务逻辑的接口：

```python
@router.post("/query")
def query_knowledge(request: QueryRequest) -> dict:
    response = get_container().query_use_case.execute(request)
    return {"code": 0, "message": "ok", "data": response.model_dump(), "trace_id": response.trace_id}
```

这个片段说明了本项目 API 层的设计风格：

1. FastAPI 自动把请求体解析成 `QueryRequest`
2. 路由函数不自己写检索逻辑
3. 而是调用 `get_container().query_use_case.execute(...)`
4. 最后把结果封装成统一 JSON 结构

也就是说，`routes.py` 的职责是：

- 接收请求
- 做轻量异常映射
- 调用 Use Case
- 返回响应

它不是业务核心。

## 8. DTO：为什么请求和响应要单独定义

文件：
[backend/src/rag_mcp/application/dto/models.py](/d:/PersonalProject/RAG-MCP/backend/src/rag_mcp/application/dto/models.py:1)

这里的 `DTO` 可以理解成：

“系统对外收发的数据模型”

比如：

```python
class QueryRequest(BaseModel):
    query: str = Field(min_length=1)
    top_k: int = Field(default=5, ge=1, le=20)
```

它的作用是：

- 限定 `query` 不能为空
- 限定 `top_k` 必须在 `1` 到 `20` 之间
- 让 FastAPI 自动校验请求

好处是很明显的：

- 前端传错参数时，框架会直接给出 `422`
- 业务层拿到的一定是结构正确的数据

同理，像 `QueryResponse`、`GenerateAnswerResponse`、`DocumentDetailResponse` 这些类，则负责规定“系统返回的数据长什么样”。

这也是为什么这个项目的 REST API 和 MCP 工具都能共享一套稳定的数据结构。

## 9. 配置系统：项目是如何知道该用哪个 Provider 的

文件：
[backend/src/rag_mcp/core/settings.py](/d:/PersonalProject/RAG-MCP/backend/src/rag_mcp/core/settings.py:1)

这个文件负责整个项目的配置加载。

### 9.1 配置从哪里来

`load_settings()` 会做这些事：

1. 加载 `.env`
2. 找到 `config/settings.yaml`
3. 读取 YAML
4. 用 Pydantic 校验
5. 转成 `Settings` 对象

核心代码片段：

```python
def load_settings(path: str | Path | None = None) -> Settings:
    load_dotenv(DOTENV_PATH)
    configured_path = path or os.getenv(SETTINGS_ENV_VAR)
    settings_path = (
        resolve_project_path(configured_path) if configured_path else ensure_default_config()
    )
    raw = yaml.safe_load(settings_path.read_text(encoding="utf-8")) or {}
    return Settings.model_validate(raw)
```

它的功能可以概括成：

- 环境变量负责敏感信息
- YAML 负责业务配置
- Pydantic 负责结构校验

### 9.2 为什么配置类这么多

你会看到很多配置类：

- `EmbeddingSettings`
- `LlmSettings`
- `VectorStoreSettings`
- `IngestionSettings`
- `RetrievalSettings`
- `RedisSettings`

这样拆分的意义是：

- 每个配置块负责一个领域
- 类型更清晰
- IDE 自动补全更好
- 配置出错时更容易定位

### 9.3 一个很关键的点：默认值

比如：

```python
class VectorStoreSettings(BaseModel):
    provider: str = "weaviate"
```

这说明如果配置文件里没写，系统就会默认把向量库 provider 当成 `weaviate`。

但要注意：

“代码默认值”不一定等于“你本地当前实际运行值”。  
如果 `config/settings.yaml` 里写的是 `chroma`，那运行时仍然会用 `chroma`。

## 10. 容器：为什么这个项目到处都在 `get_container()`

文件：
[backend/src/rag_mcp/core/container.py](/d:/PersonalProject/RAG-MCP/backend/src/rag_mcp/core/container.py:1)

这是整个项目最关键的文件之一。

如果你只看一个文件来理解系统“怎么装起来”，那就是它。

### 10.1 什么是容器

这里的 `ApplicationContainer` 可以理解成：

“把系统需要的所有组件统一创建并连接起来的地方”

比如它会创建：

- 配置对象
- Trace 收集器
- 文档仓库
- Chunk 仓库
- 向量库
- BM25 稀疏索引
- Embedding Provider
- LLM Provider
- Prompt Builder
- Ingestion Pipeline
- Retrieval Service
- 各种 Use Case

### 10.2 为什么要有容器

如果没有容器，每个接口都要自己 new 一堆对象：

- 自己读配置
- 自己建向量库
- 自己建仓库
- 自己建检索服务

那代码会很快失控。

有了容器之后：

- 创建逻辑集中
- 依赖关系清晰
- 测试更容易替换组件
- 路由和 Use Case 更干净

### 10.3 容器装配的关键片段

```python
self.vector_store = self._create_vector_store()
self.sparse_index = JsonBm25Store(vector_store_dir / "bm25_index.json")
self.reranker = create_reranker(self.settings)
self.llm_provider = create_llm_provider(self.settings)
```

这一段的功能是：

- 创建稠密检索用的向量库
- 创建稀疏检索用的 BM25 索引
- 创建重排器
- 创建大模型 Provider

也就是说，这个系统的“检索与生成引擎”是在容器里被拼起来的。

### 10.4 向量库是怎么切换的

看 `_create_vector_store()`：

```python
if provider == "memory":
    return InMemoryVectorStore()
if provider == "chroma":
    return ChromaVectorStore(...)
if provider == "weaviate":
    return WeaviateVectorStore(...)
```

这段代码非常重要，因为它体现了项目的一个核心设计：

“上层逻辑不关心底层到底是 Chroma 还是 Weaviate”

上层只关心：

- 能不能 `upsert`
- 能不能 `query`
- 能不能 `delete_by_document`

这就是“面向抽象编程”的工程价值。

### 10.5 为什么 `get_container()` 要加缓存

```python
@lru_cache(maxsize=1)
def get_container() -> ApplicationContainer:
    return ApplicationContainer(load_settings())
```

这表示：

- 整个进程里默认只创建一个容器实例
- 避免每个请求都重复初始化所有组件

这也是为什么路由里可以放心调用 `get_container()`。

## 11. 领域模型：系统内部最核心的数据长什么样

文件：
[backend/src/rag_mcp/domain/entities/models.py](/d:/PersonalProject/RAG-MCP/backend/src/rag_mcp/domain/entities/models.py:1)

这里定义的是系统内部最基础的业务对象。

最重要的几个对象：

- `Document`
  表示一个原始文档
- `Chunk`
  表示文档切出来的一段文本
- `ChunkRecord`
  表示已经带上向量、准备持久化的 Chunk
- `RetrievalResult`
  表示一次检索命中的结果
- `SourceTrace`
  表示给最终答案附带的来源信息

### 11.1 为什么 `Chunk` 和 `ChunkRecord` 要分开

这是初学者很容易忽略的一个设计点。

`Chunk` 更像“文本切分结果”：

- 有起止位置
- 有 chunk_index
- 还没有向量

`ChunkRecord` 更像“准备入库的检索记录”：

- 有文本
- 有向量
- 有 metadata

这两者分开之后，摄取流程会更清晰：

1. 先 split 出 `Chunk`
2. 再 embed 成 `ChunkRecord`
3. 再持久化

## 12. 文档摄取流程：一个文件是怎么进入知识库的

文件：
[backend/src/rag_mcp/infrastructure/pipeline.py](/d:/PersonalProject/RAG-MCP/backend/src/rag_mcp/infrastructure/pipeline.py:1)

这个文件定义了摄取管线 `IngestionPipeline`。

### 12.1 摄取主流程

核心代码片段：

```python
validated_path = self._validate_source(file_path, trace)
precheck = self._precheck_skip(str(validated_path), trace, replace_existing=replace_existing)
document = self._load_document(str(validated_path), trace)
decision = self._decide_ingestion_action(document, trace, replace_existing=replace_existing)
prepared = self.prepare(document, trace)
return self.persist(prepared, trace, decision=decision)
```

这基本就是整个摄取链路。

可以翻译成自然语言：

1. 先检查文件是否合法
2. 看看是不是完全没变，能不能直接跳过
3. 如果不跳过，就真正加载文件内容
4. 判断这次是新建、替换还是跳过
5. 切块并生成向量
6. 写入文档仓库、Chunk 仓库、向量库、BM25 索引

### 12.2 为什么有 “skip”

`_precheck_skip()` 和 `_decide_ingestion_action()` 的存在说明：

这个项目不是无脑重复导入。

如果文件路径相同、内容也没变化，它会跳过不必要的工作。  
这样可以避免：

- 重复切块
- 重复 embedding
- 重复写入索引

这就是文档里提到的“幂等摄取”。

### 12.3 `prepare()` 做了什么

```python
chunks = self.splitter.split(document)
vectors = self.embedding_provider.embed_texts([chunk.text for chunk in chunks])
```

这里的功能就是：

- 把大文档切成小块
- 把每个小块转成向量

然后再把文本块和向量组装成 `ChunkRecord`。

### 12.4 `persist()` 做了什么

```python
self.document_repository.save(document)
self.chunk_repository.save_many(prepared.chunks)
self.vector_store.upsert(prepared.records)
self.sparse_index.upsert(prepared.records)
```

这说明摄取不是只写一个地方，而是同时更新四类存储：

- 文档元数据
- 文本块
- 稠密向量索引
- 稀疏 BM25 索引

所以一个文档被 ingest 成功，意味着它已经进入了完整检索体系。

## 13. 查询流程：问题是怎么变成检索结果的

它不直接做向量检索，而是：

## 14. 混合检索：为什么既有向量库又有 BM25

文件：
[backend/src/rag_mcp/domain/services/hybrid_retrieval.py](/d:/PersonalProject/RAG-MCP/backend/src/rag_mcp/domain/services/hybrid_retrieval.py:1)

这个文件实现了“混合检索”。

### 14.1 Dense 和 Sparse 是什么

这里你需要先知道两个概念：

- Dense Retrieval
  通过向量相似度找内容
- Sparse Retrieval
  通过关键词匹配找内容，例如 BM25

Dense 擅长语义相似。  
Sparse 擅长关键词命中。  
混合检索就是把两者结合。

### 14.2 这个服务的主流程

```python
query_vector = self.embedding_provider.embed_texts([query])[0]
dense_results = self.vector_store.query(...)
sparse_results = self.sparse_index.query(...)
fused = self._rrf_fuse(...)
```

这几行就是混合检索的主干：

1. 先把用户问题变成向量
2. 用向量库做 dense 检索
3. 用 BM25 做 sparse 检索
4. 用 RRF 把两路结果融合

### 14.3 RRF 是什么

`RRF` 全称 `Reciprocal Rank Fusion`。

你可以不用先记住数学公式，只要理解：

- dense 有一个排名
- sparse 有一个排名
- RRF 把两份排名合并成一份更稳的排名

这比“只信某一路结果”通常更鲁棒。

### 14.4 rerank 在哪里发生

```python
if self.settings.rerank_enabled and self.reranker is not None and fused:
    reranked = self.reranker.rerank(...)
```

这一步代表：

- 先粗召回一批结果
- 再做一次“重排”

重排器会尝试把最相关的结果往前放。

所以完整查询链路不是“只查一次”，而是：

1. 检索
2. 融合
3. 可选重排

## 15. 问答流程：为什么生成答案前要先查一次

文件：
[backend/src/rag_mcp/application/use_cases/generate_answer.py](/d:/PersonalProject/RAG-MCP/backend/src/rag_mcp/application/use_cases/generate_answer.py:1)

`GenerateAnswerUseCase` 是“基于知识库生成答案”的总编排器。

### 15.1 先查，再答

这个 Use Case 的第一步不是调 LLM，而是：

```python
query_response = self.query_use_case.execute(
    QueryRequest(query=request.query, top_k=request.top_k)
)
```

也就是说：

- 生成答案之前
- 先把检索结果拿到

这是 RAG 的核心，不是可选项。

### 15.2 Prompt 是怎么来的

```python
rendered_prompt = self.answer_prompt_builder.build(
    query=request.query,
    source_items=source_payload,
)
```

这一段的功能是：

- 把用户问题
- 加上检索到的来源片段
- 渲染成真正发给大模型的 Prompt

这也解释了为什么仓库里有 `config/prompts/answer_system.txt` 和 `config/prompts/answer_user.txt`。

### 15.3 调用大模型

```python
answer = self.llm_provider.generate(
    rendered_prompt.user_prompt,
    system_prompt=rendered_prompt.system_prompt,
    metadata={...},
)
```

这里才是真正触发生成答案的地方。

### 15.4 为什么有 fallback

如果模型失败了，这段逻辑会走降级：

```python
except ProviderError as exc:
    answer = self._build_fallback_answer(query_response)
```

也就是说，即使 LLM 出错，系统也尽量不直接崩，而是退回到“基于检索结果的降级回答”。

这对后端系统很重要，因为它意味着：

- 服务更稳定
- 用户不一定只看到 500
- 追踪里还能记录这次是 fallback

## 19. MCP：为什么这个项目除了 API 还有 MCP

文件：
[backend/src/rag_mcp/mcp/sdk_server.py](/d:/PersonalProject/RAG-MCP/backend/src/rag_mcp/mcp/sdk_server.py:1)

如果你没接触过 MCP，可以先把它想成：

“给 Agent 用的工具协议层”

REST API 更像“给 Web 或脚本用的接口”。  
MCP 更像“给智能体平台接工具用的接口”。

### 19.1 MCP 工具函数长什么样

比如：

```python
def knowledge_query(
    query: Annotated[str, Field(min_length=1)],
    top_k: TopK = 5,
) -> QueryResponse:
    return get_container().query_use_case.execute(QueryRequest(query=query, top_k=top_k))
```

这段代码很像 API 路由，但它不是 HTTP 路由。  
它是 MCP 的工具函数。

### 19.2 为什么说它和 API 共用业务层

你会发现：

- REST API 调的是 `query_use_case.execute(...)`
- MCP 工具调的也是 `query_use_case.execute(...)`

这说明协议层和业务层是分离的。

换句话说：

- API 层只是一个入口
- MCP 层只是另一个入口
- 真实业务逻辑只有一套

这是很好的工程设计。

### 19.3 MCP 服务器是怎么注册工具的

```python
for tool in SDK_TOOLS:
    server.add_tool(tool, name=tool.__name__, structured_output=True)
```

这段代码的作用是：

- 把一组 Python 函数注册成 MCP 工具
- 让外部 MCP Client 能发现并调用它们

## 21. 一次完整请求是怎么流动的

这一节把前面的内容串起来。

### 21.1 摄取请求流

当你调用 `/api/v1/ingest` 时，流程大致是：

1. `main.py` 创建 FastAPI 应用
2. `routes.py` 接到 `/api/v1/ingest`
3. `IngestRequest` 校验请求体
4. 路由调用 `get_container().ingest_use_case.execute(...)`
5. `IngestDocumentUseCase` 调用 `IngestionPipeline`
6. `IngestionPipeline` 做验证、预检查、加载、切块、向量化、落库
7. Trace 被写入 `traces.jsonl`
8. 结果返回给客户端

### 21.2 查询请求流

当你调用 `/api/v1/query` 时，流程大致是：

1. 路由接收请求
2. DTO 校验参数
3. `QueryKnowledgeUseCase` 创建 Trace
4. `HybridRetrievalService` 执行 embedding、dense 检索、sparse 检索、融合、重排
5. Use Case 构建 `results` 和 `sources`
6. 返回统一响应

### 21.3 问答请求流

当你调用 `/api/v1/answers/generate` 时，流程大致是：

1. 先走一遍查询 Use Case
2. 再用 Prompt Builder 构建 Prompt
3. 再调用 LLM Provider
4. 如果失败则走 fallback
5. 写入 answer_generation Trace
6. 返回答案与来源

## 24. 这个项目最值得记住的工程思想

如果你读完整个仓库后，只想记住最重要的几件事，我建议记这几条：

### 24.1 协议层和业务层分离

REST API、MCP 都只是入口。  
真正的业务逻辑在 Use Case 和领域服务里。

### 24.2 配置驱动 Provider 选择

系统不把 `Weaviate`、`Chroma`、`stub LLM`、`deepseek` 直接写死在业务逻辑里，而是通过配置和工厂来切换。

### 24.3 摄取、检索、生成都可追踪

不是“能跑就行”，而是每个关键动作都尽量留下 Trace。

### 24.4 数据存储分层明确

- JSON 仓库负责文档和 Chunk 元数据
- 向量库存稠密索引
- BM25 存稀疏索引
- Trace 和评测报告各自独立持久化

### 24.5 这是一个后端工程，不是脚本集合

你会看到：

- 配置层
- 容器层
- 应用层
- 领域层
- 基础设施层
- 观测层
- 测试层

这说明项目的目标不是“做一次演示”，而是“持续维护和演进”。
