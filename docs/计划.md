## 一、项目落地场景方案（任务二）

当前项目是一个具备完整能力的但尚未落地的 RAG + MCP 服务。以下为高度契合项目现有能力边界的 5 个落地方向，按推荐优先级排列。

### 方向一：个人知识库助手（⭐ 推荐，最低摩擦）

**场景描述**：用户将个人笔记（Obsidian/Logseq 导出的 md）、论文 PDF、技术文档摄入本地 Chroma 向量库，通过 Claude Desktop 或其他 MCP Client 直接调用 MCP 工具进行语义搜索和知识问答。

**契合理由**：
- 项目已完整支持 MCP `stdio` 传输，Claude Desktop 原生支持，无需额外网络配置
- txt/md/pdf 摄入开箱即用
- 本地 Chroma 向量库无需外部服务，零依赖部署
- 6 个 Skill 覆盖了从摄入到问答的完整闭环

**当前缺口**：
- 需要编写 Claude Desktop `claude_desktop_config.json` 配置模板
- 需要一篇面向终端用户的使用指南（如何安装、配置、摄入文档、开始提问）

**预估开发量**：极低（主要是文档和配置模板编写）

**适合简历展示的角度**："为 Claude Desktop 开发了 MCP 知识库插件，实现了本地文档的语义检索与 AI 问答"

---

### 方向二：开源项目文档智能问答（⭐ 推荐，有展示价值）

**场景描述**：将任意开源项目（如 FastAPI、React、LangChain）的文档批量摄入，构建文档知识库。开发者通过 MCP 工具在 IDE 或聊天界面中直接对文档提问（如 "FastAPI 的 middleware 怎么用？"），系统从索引中检索相关段落并生成带引用的回答。

**契合理由**：
- 项目设计初衷即为"AI Agent 检索外部知识"场景
- `ingestion` Skill 支持幂等摄取和 `force_rebuild`，适合文档版本更新
- 评测框架（HitRate@K、MRR）可用于持续验证检索质量
- REST API + MCP 双入口，适用面广

**当前缺口**：
- 需要一个 Web 文档递归抓取/下载脚本（不属于项目核心，可作为 companion tool）
- 需要处理 Web 文档的 HTML→Markdown 转换
- 可以选择一个热门开源项目制作完整 Demo

**预估开发量**：低至中（主要是文档抓取脚本 + Demo 配置）

**适合简历展示的角度**："构建了开源项目文档的 RAG 智能问答系统，支持 MCP 协议接入 AI Agent，附带完整 Demo"

---

### 方向三：企业内网知识库 REST 服务

**场景描述**：小团队或企业内部部署，将规章制度、技术规范、项目文档统一摄入，提供 REST API 给内部工具调用，Dashboard 给管理员做数据观测，MCP 端点给 AI 助手接入。

**契合理由**：
- 项目已具备 REST + MCP + Dashboard 三类入口，开箱即用
- `document_management` Skill 提供完整 CRUD 能力
- 评测框架可用来持续验证检索质量
- Skill 门控机制支持按需启用/禁用功能模块

**当前缺口**：
- 认证/授权层（FastAPI middleware 可实现）
- 多用户/多集合隔离
- 生产级部署方案（Dockerfile、docker-compose）
- 数据库替代 JSON 文件持久化（SQLite 或 PostgreSQL）

**预估开发量**：中

**适合简历展示的角度**："设计并实现了企业级知识库 REST 服务，支持多协议接入、可插拔 Skill 架构和完整观测能力"

---

### 方向四：学术论文检索与综述生成

**场景描述**：研究人员批量摄入某领域的 PDF 论文，用自然语言提问（如 "这些论文中关于 XX 方法的结论是什么？"），系统检索相关段落并由 LLM 生成带引用的综述回答。

**契合理由**：
- PDF 解析已实现（`PdfDocumentLoader`）
- RRF 混合检索 + Rerank 适合学术文献的精确匹配需求
- 溯源能力来自 chunk 元数据（文档来源可追溯）
- 评测框架可验证检索质量

**当前缺口**：
- PDF 复杂排版（双栏、图表混排）解析精度有待提升
- 论文元数据自动提取（作者、年份、期刊等）
- 多模态（图表理解）仍是骨架，对学术图表暂时无法处理
- 长文档（>50页论文）的 chunk 策略可能需要调优

**预估开发量**：中至高

**适合简历展示的角度**："基于 RAG 构建了学术文献智能检索与综述生成系统，支持 PDF 论文的语义搜索与引证回答"

---

### 方向五：MCP 工具市场 / PyPI 标准化发布

**场景描述**：将项目封装为标准 MCP Server 包，发布到 PyPI，任何支持 MCP 的 AI 应用（Claude Desktop、Cursor、Continue 等）一键安装后即可获得知识库能力。

**契合理由**：
- 项目已完整实现 MCP SDK 集成，6 个 Skill 覆盖知识库管理完整生命周期
- `streamable-http` 和 `sse` 传输支持远程部署场景
- SkillRegistry 机制天然适合作为可配置的 MCP 工具集

**当前缺口**：
- PyPI 包发布配置（`pyproject.toml` 已有基础，需补充完善）
- MCP Server 注册/发现机制的适配（如 `mcp hub` 或相关 registry）
- 安装引导脚本（CLI wizard 或 `rag-mcp init` 命令）
- 用户文档和 Quick Start 指南

**预估开发量**：中（主要是打包、发布和文档工作）

**适合简历展示的角度**："开发并发布了开源 MCP 知识库工具包，支持 pip install 一键安装，服务于 MCP 生态"

## 二、代码分析文档规划（任务三）

### 目标读者

- 能读懂 Python 代码（了解类、函数、装饰器、类型注解等基础语法）
- 不了解 FastAPI、MCP 协议、分层架构、依赖注入、DDD 等工程概念
- 没有架构设计和大型项目开发经验

### 编写原则

1. **每个概念都先给一个非技术的类比**，再展示代码——用日常生活场景解释工程概念
2. **用具体代码路径讲抽象概念**——例如讲"协议层薄、应用层厚"时，直接对比 `routes.py`（薄，只有参数校验和调用）和 `use_cases/`（厚，包含业务逻辑）
3. **控制代码片段长度**——每个代码示例不超过 25 行，重点标注核心行，避免大段粘贴
4. **预判读者困惑点**——在读者可能产生疑问的地方主动插入解释（如"为什么 settings.yaml 少了很多字段程序还能跑？"）
5. **用 ASCII 流程图串联组件**——在关键位置用文本流程图展示数据流和控制流

### 关键设计决策

**Q: 为什么第一章用"跟随一个请求"的方式开头，而不是先讲架构理论？**

A: 目标读者缺乏架构经验。如果先用抽象概念（分层、DI、实体、仓储）轰炸，读者会在前几页就放弃。先让他们看到一个具体的请求"从哪里进、经过谁、到哪里去"，脑子里有一个具象的图景，后面各章再逐个解释途中遇到的每个组件是干什么的。

**Q: 为什么把 MCP 放在第五章而不是更靠前？**

A: MCP 是项目的核心亮点，但它依赖前面四章建立的架构理解。如果读者不知道 Skill 是什么、Container 是干什么的，直接讲 MCP 会是空中楼阁。前四章是"积木"，第五章用这些积木"搭出" MCP 的完整图景。

**Q: 第三章（DI）放在架构章之后、Skill 之前，是否合理？**

A: 是的。读者先看到"代码分了很多层"（第二章），自然会问"这些层之间怎么互相调用？"——这正是第三章要回答的。理解了 DI 之后，Skill 机制（第四章）的 `wire_container()` 方法才不会显得神秘。
