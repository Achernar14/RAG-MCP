# RAG-MCP 改进计划

> 基于架构重构完成后的代码现状制定。每条改进独立可验证，按优先级分阶段。

---

## 阶段一：低风险、立竿见影（1-2 天）

### 1.1 批量 Embedding

**现状**：`zhipu_embedding.py` 逐条调 API，20 个文本 = 20 次 HTTP 往返。

**改成**：一次 POST 传 `input: ["text1", "text2", ...]`。

**改动范围**：仅 `infrastructure/embedding/zhipu_embedding.py` 的 `embed_texts()`。

**验收**：ingest 一个 20-chunk 的文档，trace 中 `embed` 阶段耗时下降 80%。

---

### 1.2 ChromaDB 锁重试精准化

**现状**：`_with_lock_retry` 捕获 `Exception`，通过字符串 `"database is locked"` 判断。非锁异常也被重试。

**改成**：只捕获 ChromaDB 的特定锁异常类型。

**改动范围**：仅 `infrastructure/vector_store/chroma_store.py`。

**验收**：非锁异常（如网络超时）不触发 0.2s × 5 次重试。

---

### 1.3 Provider 继承 ABC 显式声明

**现状**：`ZhipuEmbeddingProvider` 没有写 `class ZhipuEmbeddingProvider(EmbeddingProvider)`，靠鸭子类型互换。

**改成**：所有 Provider 显式继承对应 ABC。

```python
class ZhipuEmbeddingProvider(EmbeddingProvider):
    ...

class HashEmbeddingProvider(EmbeddingProvider):
    ...
```

**改动范围**：各 `infrastructure/embedding/*.py`、`infrastructure/llm/*.py`、`infrastructure/rerank/*.py`。

**验收**：`isinstance(provider, EmbeddingProvider)` 返回 `True`，IDE 提供方法补全提示。

---

### 1.4 BM25 改为 SQLite FTS5

**现状**：`JsonBm25Store`，120 行纯 Python。O(n) 遍历所有 chunk 算 BM25，每次 upsert 全量 JSON 写盘。百级 chunk 可用，千级以上开始慢。

**改成**：SQLite FTS5——零新增依赖（Python 标准库 `sqlite3`），增量写入，倒排索引查询，内置 `bm25()` 分数函数。

**改动范围**：

```
新增 infrastructure/sparse/sqlite_fts_store.py   (~80 行)
settings.yaml 新增 sparse.provider: "sqlite_fts"
collection_manager.py 的 _build_scope 按配置选 JsonBm25Store / SqliteFtsStore
```

**核心实现**：

```python
class SqliteFtsStore:
    def __init__(self, db_path):
        self.conn = sqlite3.connect(str(db_path))
        self.conn.execute(
            "CREATE VIRTUAL TABLE IF NOT EXISTS bm25 "
            "USING fts5(chunk_id, document_id, text, metadata)"
        )

    def upsert(self, records):
        with self.conn:
            for r in records:
                self.conn.execute(
                    "INSERT INTO bm25 VALUES (?, ?, ?, ?)",
                    (r.id, r.document_id, r.text, json.dumps(r.metadata)))

    def query(self, query_text, top_k):
        rows = self.conn.execute(
            "SELECT chunk_id, text, metadata, bm25(bm25) AS score "
            "FROM bm25 WHERE bm25 MATCH ? ORDER BY score LIMIT ?",
            (query_text, top_k)).fetchall()
        return [RetrievalResult(
            chunk_id=row[0], text=row[1], metadata=json.loads(row[2]),
            score=1/(1+abs(row[3])), retrieval_method="sparse"
        ) for row in rows]
```

**中文分词**：FTS5 内置 `unicode61` tokenizer 对中文是逐字分割（"知识库"→"知/识/库"）。检索时调用方先用 jieba 分词后用空格连接：

```python
# _wire_ingestion 中 upsert 前：
import jieba
processed_text = " ".join(jieba.cut(record.text))

# query 时：
processed_query = " ".join(jieba.cut(query_text))
```

**验收**：1000 个 chunk 下 `sparse_retrieval` 阶段耗时 < 5ms（当前 ~50ms），`upsert` 不再触发全量 JSON 写盘。

## 阶段二：检索质量提升（3-5 天）

### 2.1 Cross-Encoder Reranker

**现状**：`LexicalReranker` 仅做词汇重叠度评分（`overlap * 0.1`），无语义排序能力。

**改成**：用 `BAAI/bge-reranker-v2-m3`（多语言，支持中英文）。

**模型选择原因**：
- M3 = Multilingual，覆盖中英文，与当前 Zhipu Embedding 的中文友好特性一致
- BAAI 系列社区验证充分（GitHub 4 万+ 星），在所有多语言 reranker 中验证最广
- 单个模型覆盖全部需求，不需语言检测路由

**改动范围**：

```
新增 infrastructure/rerank/cross_encoder_reranker.py  (~40 行)
pyproject.toml 加 sentence-transformers 依赖
factories.py 注册 "cross_encoder" → _create_cross_encoder_reranker
settings.yaml 中 rerank.provider 切换 "lexical" / "cross_encoder"
```

**核心实现**：

```python
from sentence_transformers import CrossEncoder

class CrossEncoderReranker(BaseReranker):
    def __init__(self, model_name="BAAI/bge-reranker-v2-m3"):
        self.model = CrossEncoder(model_name, max_length=512)

    def rerank(self, query, results, top_k):
        pairs = [[query, r.text] for r in results]
        scores = self.model.predict(pairs, show_progress_bar=False)
        ranked = sorted(zip(results, scores), key=lambda x: x[1], reverse=True)
        return [r for r, _ in ranked[:top_k]]
```

**首次启动**：自动下载模型到 `~/.cache/huggingface/`（~2.3GB），之后从缓存加载。内存占用 ~2.3GB。

**验收**：评测数据集（`rag_mcp_golden_test_set.json`）中 Hit Rate@5 和 MRR 有可测量的提升。建议跑 `POST /api/v1/evaluations/run` 获取基线 → 切换 → 再跑一次 → 对比。

---

### 2.2 Query Rewrite（查询改写）

**现状**：用户查询直接用于 Embedding 和 BM25 检索。口语化、有歧义、指代不明的查询（"它为什么这么贵"）检索效果差。

**改成**：在 `search_knowledge` handler 中增加可选步骤——用 LLM 把原始查询改写成精确的书面表达。

**改动范围**：

```
application/handlers.py: search_knowledge 增加可选 rewrite 步骤
settings.yaml: retrieval.query_rewrite_enabled: false  (默认关闭)
```

**流程**：

```
用户 query: "它为什么这么贵"
  → LLM Rewrite: "iPhone 15 Pro Max 定价偏高的原因是什么"
  → Embedding + BM25 → 检索
  → 结果质量显著提升
```

**配置**：复用现有 `llm_provider`，不引入新的 LLM 依赖。

**验收**：人工构造 5 条模糊查询（含指代不明、口语化），对比开启前后的检索结果。Rewrite 后的 Top-5 应该更相关。

## 阶段三：质量实验（后续按需）

### 3.1 父子切割（Parent-Child Chunking）

切两份：子 chunk（150 token，精检索）+ 父 chunk（500 token，回给 LLM）。入库只建子 chunk 向量索引，检索命中后根据 `parent_id` 取父 chunk。

**适用场景**：回答需要完整上下文的问题（"这个函数是怎么实现的"），小块精检索 + 大块回 LLM 组合效果最好。

**建议**：在 Cross-Encoder Reranker 和 Query Rewrite 生效后，用评测数据对比父子切割 vs 当前单一切割的指标。

### 3.2 HyDE（Hypothetical Document Embeddings）

LLM 先根据问题生成假设答案 → 用假设答案做 Embedding → 检索。学术验证有效，但多一次 LLM 调用的延迟换取精度。建议在 Query Rewrite 基础上评估是否还需要。

### 3.3 三路并行（多 Query 扩展）

Dense + Sparse + LLM 生成 3 个改写版本各自检索。在两路基础上加第三路的边际收益需要评测验证。建议先落地 Query Rewrite，评测数据说话。

---

## 不改的项目及理由

| 条目 | 理由 |
|------|------|
| 文本切分器换 LangChain | 当前 `SimpleTextSplitter` 能力同 `RecursiveCharacterTextSplitter` 等价，换库不增实质提升。升级方向是加语义边界检测（spaCy 句子分割），可在当前 splitter 上增量改 |
| 引入 Elasticsearch | 重量级外部依赖。SQLite FTS5 零依赖覆盖同一场景 |
| 切分器性能优化 | 当前 O(n) 单次扫描不是瓶颈（embedding API 调用才是）。有具体 profile 数据后再议 |
| 视觉 LLM | `_build_multimodal_asset_skeleton` 返回空列表，`vision_llm.provider: "disabled"`。保留或删除都不影响系统。暂不花时间 |
