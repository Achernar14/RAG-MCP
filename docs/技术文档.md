2. 说明项目现在明确支持什么、不支持什么。
3. 说明后续修改必须遵守哪些结构约束。

## 2. 项目定位

`RAG-MCP` 是一个面向本地知识库与 AI Agent 集成场景的模块化 RAG 服务。

项目核心目标：

- 提供文档摄取、切分、向量化、索引、检索、重排、回答生成能力。
- 通过 MCP 协议向外部 AI Agent / MCP Client 暴露知识工具。
- 通过 REST API 与 Dashboard 提供本地管理、调试、验证与观测入口。
- 保持清晰的分层、可替换的 Provider 边界、可测试的工程结构。

一句话定义：

> 本项目是一个面向 AI Agent / MCP Client 的知识上下文服务层与 RAG 能力底座。

---

## 3. 非目标

当前项目明确不是：

- 通用多租户 AI 平台
- 完整业务后台系统
- 面向生产大规模集群的部署平台
- 已完成的多模态 RAG 系统
- 已完成的 LLM-as-Judge 评测平台

这些方向可以在后续演进中扩展，但都不属于当前代码的既有边界。

## 4. 当前架构总览

项目当前采用分层架构，并在应用装配层引入 Skill 模块化机制。

### 4.1 分层结构

```text
Presentation
├── FastAPI REST API
├── MCP SDK Server
└── Dashboard

Application
├── Use Cases
└── DTO Models

Domain
├── Entities / Value Objects
├── Service Abstractions
└── Repository Contracts

Infrastructure
├── Providers
├── Vector Stores
├── Sparse Index
├── Repositories
├── Pipeline / Loader / Splitter
└── Prompt / Redis / Trace Persistence

Assembly
├── ApplicationContainer
└── SkillRegistry
```

### 4.2 当前装配方式

当前容器装配分为两步：

1. 先装配共享基础设施，例如 settings、trace、repositories、vector store、providers、Redis。
2. 再根据 `settings.skills` 启用具体 Skill，并由各 Skill 自己完成 use case 和工具注册。

代码事实对应：

- `SkillRegistry`：`backend/src/rag_mcp/core/skill_registry.py`
- 容器装配：`backend/src/rag_mcp/core/container.py`
- Skill 实现：`backend/src/rag_mcp/skills/*`

这意味着当前项目已经不再是"单容器一次性装配全部业务"的结构，而是"共享基础设施 + 按 Skill 接线"的结构。

> **关于 pydantic 默认值**：`settings.yaml` 中可以省略某些配置块（如 `skills:`、`redis:`、`mcp.transport` 等），此时 pydantic 模型 `Settings` 会使用 [settings.py](../backend/src/rag_mcp/core/settings.py) 中定义的默认值。因此"配置文件中看不到某个字段"不等于"该功能不存在"——应始终以 pydantic 模型定义为准，yaml 文件只覆盖模型默认值。

## 5. Skill 架构

当前内置 6 个 Skill：

| Skill | 职责 | 主要依赖 | 对外能力 |
| --- | --- | --- | --- |
| `ingestion` | 文档摄取、知识状态、集合重建、集合列表 | embedding、vector store、BM25、document/chunk repo | REST + MCP |
| `retrieval` | Dense + Sparse 混合检索、RRF、Rerank | ingestion 基础设施、reranker | REST + MCP |
| `generation` | 基于检索结果的回答生成 | retrieval、LLM、Prompt | REST + MCP |
| `document_management` | 文档列表、摘要、详情、删除 | repositories、索引删除能力 | REST + MCP |
| `evaluation` | 检索评测、报告持久化与查询 | retrieval、evaluation repo | REST + MCP |
| `observability` | Trace 浏览与 Dashboard 观测 | trace persistence | REST + MCP + Dashboard |

每个 Skill 在 `backend/src/rag_mcp/skills/<skill_name>/__init__.py` 中独立实现，包含三个核心方法：

- `descriptor()`：声明 Skill 元数据（名称、版本、依赖关系）
- `wire_container()`：向容器注入该 Skill 所需的 use case 和基础设施
- `register_tools()`：返回该 Skill 暴露给 MCP 的工具列表

### 5.1 Skill 启停

当前支持通过 `settings.yaml` 中的 `skills` 配置块按能力启停：

```yaml
skills:
  ingestion: true
  retrieval: true
  generation: true
  document_management: true
  evaluation: true
  observability: true
```

> **注意**：如果 `settings.yaml` 中未显式写入 `skills:` 配置块（当前实际配置文件即如此），pydantic 模型 `SkillSettings` 将使用默认值——所有 Skill 均为 `true`（全部启用）。这意味着 Skill 门控机制在代码层面已就绪，但开关目前由 pydantic 默认值驱动，而非 yaml 显式配置。如需精确控制启停，应在 `settings.yaml` 中显式添加 `skills:` 块。

### 5.2 Skill 门控规则

- MCP 只暴露已启用 Skill 的工具。
- REST 路由通过 `_require_skill()` 做运行时门控。
- 关闭某个 Skill 后，相关路由与工具不再视为可用能力。

因此，能力边界应始终以"代码存在且对应 Skill 已启用"为准。

## 6. 对外入口

项目当前有三类正式入口。

### 6.1 REST API

入口文件：

- `backend/src/rag_mcp/main.py`
- `backend/src/rag_mcp/api/v1/routes.py`

当前路由按 Skill 归类：

- `health`
- `ingest`
- `stats`
- `collections`
- `query`
- `answers/generate`
- `documents`
- `evaluations`
- `traces`

### 6.2 MCP

入口文件：

- `backend/src/rag_mcp/mcp/sdk_server.py`
- `backend/src/rag_mcp/mcp/server.py`

当前 MCP 基于官方 `FastMCP`，并支持三种传输：

- `stdio`
- `streamable-http`
- `sse`

**关于传输配置的默认值说明**：

- pydantic 模型 `McpSettings` 的 `transport` 默认值为 `"stdio"`（见 [settings.py](../backend/src/rag_mcp/core/settings.py)）。
- [settings.yaml.example](../config/settings.yaml.example) 中推荐设置为 `"streamable-http"`。
- 当前实际 [settings.yaml](../config/settings.yaml) 中 `mcp:` 块仅包含 `server_name` 和 `server_version`，其余字段（`transport`、`host`、`port`、`mount_path`）均由 pydantic 默认值提供。

默认推荐：

- 本地工具调用使用 `stdio`
- 远程接入或统一服务部署使用 `streamable-http`

> **补充说明**：`backend/src/rag_mcp/mcp/tools/` 目录当前为空目录。MCP 工具并非存放在该目录中，而是由各 Skill 的 `register_tools()` 方法在运行时动态生成 ToolDescriptor 列表，再通过 [sdk_server.py](../backend/src/rag_mcp/mcp/sdk_server.py) 中的 `_build_fastmcp_server()` 统一注册到 FastMCP 实例。该空目录是历史遗留，不影响功能。

### 6.3 Dashboard

入口文件：

- `backend/src/rag_mcp/observability/dashboard/app.py`

当前 Dashboard 主要承担可视化观测和本地运维入口职责，不承载核心业务逻辑。

当前页面包括：

- `Overview`
- `Ingestion Manager`
- `Answers`
- `Documents`
- `Traces`
- `Evaluations`

## 7. 当前已实现能力

本节只描述当前代码已经落地的能力边界。

### 7.1 摄取与索引

当前已经支持：

- `txt`、`md`、`pdf` 文档加载
- 本地文件合法性校验
- 文本标准化
- 文本切块与基础边界优化
- Embedding 写入
- 向量索引持久化
- BM25 稀疏索引持久化
- 文档与 chunk 元数据持久化
- 基于文件内容变化的幂等摄取
- `force_rebuild` 触发替换式重建

当前基础元数据已覆盖：

- 文件名、扩展名、大小、修改时间
- 路径与内容指纹
- 行数、词数、非空字符数
- 是否包含 CJK
- loader 类型

### 7.2 检索

当前已经支持：

- Dense Retrieval
- Sparse Retrieval
- RRF 融合
- Lexical Rerank
- 统一 `results + sources + trace_id` 查询响应

当前实现中，查询能力属于 `retrieval` Skill，不应直接在协议层重复实现业务逻辑。

### 7.3 生成式问答

当前已经支持：

- `GenerateAnswerUseCase`
- 基于检索结果构造 Prompt
- 模板化 `system prompt / user prompt`
- LLM 生成失败时回退到基于检索结果的降级回答
- 返回 `answer + sources + trace`

### 7.4 文档管理

当前已经支持：

- 文档列表
- 文档摘要
- 文档详情
- 文档删除
- 集合信息查询
- 集合重建
- 知识状态统计

### 7.5 可观测性

当前已经支持：

- ingestion / query / answer_generation / evaluation trace 持久化
- trace 列表与 trace 详情查询
- Dashboard 基础观测能力
- 基础失败聚合、阶段耗时与结果摘要展示

### 7.6 评测

当前已经支持：

- 检索评测 MVP
- Golden test set 加载
- `HitRate@K`
- `MRR`
- 评测报告持久化
- 评测报告列表与详情查询

### 7.7 Provider 与运行时基础设施

当前已经支持：

- Embedding Provider：测试占位与真实 Provider 双路径
- LLM Provider：测试占位与真实 Provider 双路径
- Reranker 工厂化创建
- Vision Provider 边界保留
- Redis 可选缓存（pydantic 模型 `RedisSettings.enabled` 默认为 `false`，当前 [settings.yaml](../config/settings.yaml) 未显式配置 `redis:` 块，Redis 处于默认关闭状态；[settings.yaml.example](../config/settings.yaml.example) 中含有完整 Redis 配置模板供开启时参考）
- Prompt 外置加载

## 8. 当前明确未完成或仅保留骨架的能力

本节用于界定"不要误认为已经完成"的部分。

### 8.1 多模态

当前仅保留多模态骨架，还没有完成真实图像提取与图文联合检索。

当前真实状态：

- PDF loader 会写入稳定的 `assets` 结构字段
- 会保留 `image_asset_count` 与 `multimodal_status`
- 当前默认状态仍是 `skeleton_only`
- 还没有真实图片抽取、图片 caption、图文联合检索闭环

这意味着代码中存在多模态相关的数据结构（如 assets 字段、multimodal_status 标记），但它们的值目前是占位性质的，仅供未来扩展使用。当前不应假设这些数据可用于任何实际的多模态检索场景。

### 8.2 高级评测

当前尚未完成：

- LLM-as-Judge
- Faithfulness 评测
- Citation Accuracy 自动评测
- Prompt / Model 横向对比评测体系

### 8.3 生产级部署能力

当前尚未形成完整的生产部署方案，包括但不限于：

- 标准化容器部署体系
- 大规模运行时监控
- 完整 SLA/告警体系
- 面向多租户或高并发场景的部署规范

### 8.4 MCP 扩展能力

当前 MCP 重点在工具暴露，不代表已经覆盖全部 MCP 扩展面。

当前未完成或未承诺的方向包括：

- resources
- prompts 资源暴露
- sampling 等更完整协议扩展

## 9. 数据与持久化边界

当前项目采用"多种轻量持久化协作"的方式，而不是统一数据库方案。

### 9.1 当前持久化构成

- 文档与 chunk 元数据：JSON 仓储
- Trace：JSONL
- 评测报告：JSONL
- Sparse Index：BM25 JSON 持久化
- Dense Vector Store：`memory` / `chroma` / `weaviate`（三者代码均已实现；当前 [settings.yaml](../config/settings.yaml) 实际使用 `chroma`，[settings.yaml.example](../config/settings.yaml.example) 配置为 `weaviate`；可通过修改 `vector_store.provider` 字段切换）

### 9.2 设计原则

- 向量检索与结构化管理分离。
- 业务层不直接依赖具体存储实现。
- 删除、重建、状态查询等管理动作优先通过仓储与 use case 完成。

## 10. 配置规范

### 10.1 配置来源

当前配置来源分为两类：

- `config/settings.yaml`：业务配置与运行参数
- `.env`：敏感环境变量

配置加载流程（见 [settings.py](../backend/src/rag_mcp/core/settings.py)）：

1. 加载 `.env` 中的环境变量
2. 读取 yaml 配置文件
3. 用 yaml 中的值覆盖 pydantic 模型的默认值
4. 缺失的配置块/字段由 pydantic 默认值兜底

因此，[settings.yaml](../config/settings.yaml) 是 **pydantic 默认值的覆盖层**，而非完整配置的唯一定义。完整的配置结构定义始终以 [settings.py](../backend/src/rag_mcp/core/settings.py) 中的 pydantic 模型为准。

### 10.2 关键配置分区

当前 pydantic 模型定义的主要配置块包括（按 `Settings` 模型中的定义顺序）：

| 配置块 | settings.yaml 中是否显式存在 | 说明 |
| --- | --- | --- |
| `app` | ✅ 存在 | 应用名称与环境 |
| `embedding` | ✅ 存在 | Embedding 维度与 provider 类型 |
| `embedding_provider` | ✅ 存在 | Zhipu API 配置 |
| `llm` | ✅ 存在 | DeepSeek API 配置 |
| `vision_llm` | ✅ 存在 | 视觉 LLM（当前 disabled） |
| `vector_store` | ✅ 存在 | 当前使用 Chroma |
| `retrieval` | ✅ 存在 | 检索参数 |
| `rerank` | ✅ 存在 | 当前使用 Lexical Rerank |
| `ingestion` | ✅ 存在 | 切分参数与文件约束 |
| `observability` | ✅ 存在 | Trace 开关与路径 |
| `evaluation` | ✅ 存在 | 评测参数与指标 |
| `prompts` | ✅ 存在 | Prompt 模板路径 |
| `mcp` | ⚠️ 部分存在 | 仅有 `server_name` 和 `server_version`，其余字段使用默认值 |
| `api` | ✅ 存在 | REST API 绑定地址 |
| `redis` | ❌ 不存在 | 使用 pydantic 默认值（`enabled: false`），完整模板见 example |
| `skills` | ❌ 不存在 | 使用 pydantic 默认值（全部启用），完整模板见 example |

### 10.3 MCP 配置

当前 MCP 配置通过 pydantic 模型 `McpSettings` 定义（默认值在 [settings.py](../backend/src/rag_mcp/core/settings.py) 中）：

| 字段 | 默认值 | 当前 yaml 是否覆盖 |
| --- | --- | --- |
| `server_name` | `"rag-mcp"` | ✅ 是 |
| `server_version` | `"0.1.0"` | ✅ 是 |
| `transport` | `"stdio"` | ❌ 否（使用默认值） |
| `host` | `"127.0.0.1"` | ❌ 否（使用默认值） |
| `port` | `9000` | ❌ 否（使用默认值） |
| `mount_path` | `"/mcp"` | ❌ 否（使用默认值） |

即：当前实际运行时使用 `stdio` 传输。如需切换到 `streamable-http` 或 `sse`，应在 `settings.yaml` 的 `mcp:` 块中显式添加 `transport`、`host`、`port`、`mount_path` 字段。完整配置示例见 [settings.yaml.example](../config/settings.yaml.example)。

### 10.4 敏感信息规则

- 真实 API Key 不写入代码。
- `settings.yaml` 只保存环境变量名或非敏感参数。
- 所有文档示例中只允许出现占位值，不允许出现真实密钥。

## 11. 开发与扩展规则

### 11.1 总体原则

- 业务优先，结构清晰。
- 协议层薄，应用层统一编排。
- 可替换性优先于厂商绑定。
- 新能力默认以 Skill 方式考虑装配边界。

### 11.2 协议层约束

REST、MCP、Dashboard 都属于 Presentation 层，因此：

- 不在路由或 MCP Tool 中直接拼装底层基础设施。
- 不在协议层重复实现业务逻辑。
- 业务行为统一进入 use case。

### 11.3 Skill 扩展约束

新增 Skill 时必须同时明确：

- Skill 名称与职责边界
- 依赖哪些已有 Skill
- 自己暴露哪些 MCP 工具
- 自己需要装配哪些 use case / service
- 是否需要 REST 路由门控

### 11.4 Provider 扩展约束

新增 Provider 时必须满足：

- 有明确抽象接口
- 能通过 settings 驱动切换
- 有失败时的可解释行为
- 能进入 trace
- 不把厂商 SDK 细节扩散到 use case

### 11.5 文档更新约束

只要出现以下变更，就必须同步更新本文档：

- 新增或删除 Skill
- 变更对外入口边界
- 变更默认 MCP 传输策略
- 变更存储方案
- 变更 Provider 配置结构
- 将骨架能力提升为正式能力

## 12. 测试与验证规则

当前项目要求维持以下测试方向：

- use case 行为测试
- provider / prompt / cache 基础设施测试
- MCP 工具测试
- MCP HTTP 传输集成测试
- FastAPI + MCP 挂载集成测试
- Dashboard service / view model 测试

本文档不再记录固定的测试数量或固定的通过数，因为这些数字会持续变化。

判断标准应改为：

- 关键主链路是否被测试覆盖
- 新增能力是否有对应测试
- 文档声称的能力是否能在代码和测试中找到支撑

## 15. 结论

截至当前代码现状，`RAG-MCP` 已经形成：

- 基于 SkillRegistry 的模块化能力装配
- 同时支持 REST、MCP、Dashboard 三类入口
- 支持 `stdio / streamable-http / sse` 的 MCP 传输模式
- 具备摄取、检索、生成、管理、评测、观测六类核心能力

同时也应明确：

- 多模态仍是骨架而非完整能力
- 高级评测仍未完成
- 部署工程化仍未完成
- 历史规划稿不再作为现状依据
- 部分配置块（`skills`、`redis`、`mcp` 的传输参数）当前由 pydantic 默认值驱动，而非 yaml 显式配置；这属于设计特性而非缺陷，但读者应知悉以免误判

后续所有文档、开发与评审，应以本文档为总指导，并持续保持与代码实现一致。
