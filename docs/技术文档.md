## 2. 项目定位

`RAG-MCP` 是一个面向本地知识库与 AI Agent 集成场景的模块化 RAG 服务，核心目标是：

- 提供文档摄取、切分、向量化、索引、检索、重排、回答生成能力。
- 通过 MCP 协议向外部 AI 客户端暴露知识上下文能力。
- 提供 REST API 与可视化运维能力，用于本地管理、调试、验证与观测。
- 形成一个可持续开发完成、可测试、可替换 Provider、可演进的工程化项目。

一句话定义：

> 本项目是一个“面向 AI Agent / MCP Client 的知识上下文服务层与 RAG 能力底座”。

## 4. 当前已落地能力

当前项目已经完成并通过测试验证的能力如下。

### 4.1 知识摄取与索引

- 文档摄取：支持 `Markdown`、`TXT`、`PDF`。
- 文档加载、切分、Chunk 持久化、向量写入、BM25 建索引主线已打通。
- 本地向量存储已接入 `Chroma`，并支持持久化目录。
- 本地稀疏索引已接入 `BM25` JSON 持久化。
- 基础幂等已落地：
  - 同路径同内容重复摄取会跳过
  - 同路径内容变更会替换旧索引而不是叠加脏数据
  - 可通过 `force_rebuild` 强制走替换重建链路
- 基础元数据增强已落地：
  - 文件名、扩展名、大小、修改时间、字节指纹、内容指纹、行数、词数、非空字符数、是否含 CJK、loader 类型
- 文件合法性校验已落地：
  - 扩展名校验
  - 空文件校验
  - 隐藏文件校验
  - 最大文件大小校验
- 跳过判断已前移到 `load` 之后、`split/embed` 之前，未变化文件不会重复执行 embedding
- 预检查式跳过已落地：
  - ingest 前先基于本地文件 `mtime / size / bytes fingerprint` 做 cheap precheck
  - 命中未变化时可直接跳过，不再进入 loader / parser
- 基础文本标准化已落地：
  - 统一换行
  - 清理重复空格与制表符
  - 保留段落级换行结构
- 基础 chunk refinement 已落地：
  - 优先尝试自然边界切分
  - 避免明显在单词中间截断
  - 过滤过短碎片 chunk，同时对短文档保留最小可用 chunk
- ingestion 策略已配置化：
  - `normalize_whitespace`
  - `preserve_paragraph_breaks`
  - `boundary_scan_chars`
  - `min_chunk_length`

### 4.2 检索与重排

- 已完成 Sparse Retrieval。
- 已完成 `RRF Fusion`。
- 已完成 `Lexical Rerank`。

  - `results`

### 4.3 管理与可观测

- 已完成 ingestion / query / evaluation / answer_generation trace 持久化。

- 已支持集合统计与集合重建。

  - Trace 页支持状态聚合摘要，覆盖 `created / replaced / skipped / fallback / error / ok`
  - Trace 页已支持 answer/query trace 跨 trace 跳转与 execution chain 排障视图
  - Trace 页已支持 failure hotspot 聚合，按 `query / provider / prompt` 查看 failure、fallback 与耗时

## 8. 当前是否符合“提取业务、重构架构”的目标

结论：**当前方向符合目标，并且已经取得实质性进展，但尚未完全达成目标。**

更具体地说：**当前实现没有偏离参考项目的业务主干。** 现阶段仍然围绕参考项目最有业务价值的主链路推进：

- 摄取
- 混合检索
- 溯源返回
- MCP / REST 暴露
- Trace / Dashboard
- 评测
- 生成式问答

### 8.1 已符合的部分

- 已经从参考项目中提取了核心主业务，而不是停留在演示级能力。
- 当前实现坚持 use case 分层、容器装配、协议层薄化，没有照搬参考项目的混乱目录和脚本式组织。
- 摄取、检索、评测、生成、管理、观测的主要链路已经具备统一入口与一致的数据流。
- Provider 接入已经开始转向配置驱动和工厂化装配，而不是在容器中持续堆叠分支逻辑。
- Prompt 已从业务逻辑中外置，为后续生成质量迭代和多模型切换留出了正确边界。

### 8.2 尚未完成的部分

- 多模态真实处理链路尚未落地，当前仅完成 PDF 资产元数据骨架。
- Dashboard 还停留在基础管理视角，离“可运维、可回归、可排障”的完整形态还有差距。
- 摄取高级增强、多集合一致性、语义级 chunk / metadata 优化仍未补齐。
- 生成评测与高级质量回归尚未建立。

因此，当前项目已经达成“从参考项目提取业务，并以更合理架构重建”的方向性要求，但仍需继续补齐剩余主流闭环，才能认为目标真正完成。

### 8.3 本轮纠偏结论

本轮文档已做以下纠偏：

- 不再把“MCP SDK 收口 / legacy 兼容层退役”误写为业务主干阻塞项，而是归类为协议层工程收敛项。
- 不再把已经落地的基础摄取增强写成“未实现”，改为“已部分完成，剩高级增强”。
- Dashboard 现状按当前六页结构与现有 trace drill-down 能力重新描述。
- 下一阶段优先级重新对齐到业务主线，而不是先做运行时替换。

## 9. 本项目总体建设原则

### 9.1 业务优先，结构规范

先保证核心业务链路完整，再保证结构正确。  
不能为了架构漂亮长期没有可运行结果，也不能为了快速跑通继续堆积耦合代码。

### 9.2 协议层、应用层、领域层、基础设施层严格分离

本项目必须以清晰边界组织代码：

- 协议层负责接收外部请求和返回格式。
- 应用层负责编排业务用例。
- 领域层负责核心规则与抽象接口。
- 基础设施层负责第三方实现与持久化细节。

### 9.3 一切能力以可替换为前提

以下能力必须可替换：

- Embedding Provider
- LLM Provider
- Vision LLM Provider
- Reranker
- Vector Store
- Sparse Index
- Loader / Splitter
- Evaluator

### 9.4 一切关键链路必须可观测

至少要能看到：

- ingest 每个阶段耗时
- query 每个阶段耗时
- evaluation 每个测试样本的结果
- generation 是否走降级路径
- rerank 前后变化
- provider 调用失败原因

### 9.5 一切输出都必须可追溯

任何面向用户或 MCP Client 的问答结果，都必须能关联：

- 原始文档
- chunk 标识
- 相关页码或位置
- 检索得分
- 文本摘录

  - Overview recent trace status summary
  - Query trace 已补充 `top_k` 元数据，便于观察链路参数
  - Answer trace 已补充 query/provider/prompt 基础观测字段，支持内部 query trace 关联、LLM provider/model 识别、Prompt 路径与指纹定位

剩余必须实现的内容：

- 在当前 answer trace 的 query / provider / prompt 基础观测之上，继续增强失败样本 drill-down 与聚合分析
- Ingestion / Query / Answer / Evaluation 进一步拆成更独立的专用排障视图
- 跨文档、跨 trace、跨 evaluation 的关联跳转继续补齐

验收标准：

- Dashboard 可以覆盖管理、调试、观测、评测四类核心动作。

### 10.4 业务主干项 D：摄取增强闭环

目标：

- 让摄取流程具备幂等性、元数据增强和后续多模态扩展能力。

当前状态：

- 基础摄取链路已完成。
- 基础内容幂等已完成：
  - 同路径同内容跳过
  - 同路径内容变更替换
- 强制重建链路已完成：
  - `force_rebuild=true` 时跳过 skip 策略，直接走 replace / cleanup / rebuild
- 基础文件元数据增强已完成。
- 基础文本标准化与基础 chunk refinement 已完成。
- 基于本地文件检查的 precheck skip 已完成。
- 基础文件合法性校验已完成。
- 深度 metadata enrichment、进一步 chunk quality 优化、失败重试策略仍未实现。

必须实现的内容：

- 强制重建 / 自动跳过策略进一步完善
- 更稳定的版本判断与失败重试机制
- 深度 Metadata Enrichment
- 更强的 Chunk Refinement / 语义级切分
- 为多模态摄取预留统一扩展点

验收标准：

- 同一路径同内容不重复摄取。
- 同一路径内容变更时支持重建。
- 失败文档和成功文档可分开处理。

### 10.5 业务主干项 E：Provider 体系扩展闭环

目标：

- 从当前 Embedding / LLM 的真实接入，扩展到更完整的 Provider 体系。

当前状态：

- Embedding 与 LLM 已接入真实 Provider。
- Prompt 已外置。
- Provider 装配已开始工厂化。

必须实现的内容：

- Vision Provider 抽象与实现
- 更强模型型 Rerank Provider 扩展实现

- 超时、错误包装、降级策略统一化

验收标准：

- 不修改 use case 即可切换 Provider。
- 新增 Provider 时只影响基础设施层与配置层。

### 10.6 业务主干项 F：高级评测与生成质量闭环

目标：

当前状态：

## 11. 当前阶段的技术决策结论

### 11.1 评测优先于更复杂生成

这个决策已经验证为正确：

- 先完成检索评测 MVP，使后续调优有基线。
- 再接真实 LLM 和生成闭环，使“检索”和“生成”的职责更清楚。

### 11.2 生成必须独立建模，不覆盖检索

这个决策继续保持：

- 检索模式提供结构化上下文。
- 生成模式在检索之上追加 Prompt、LLM、回答回填。
- 不能让“生成接口”取代“检索接口”。

### 11.3 Prompt 必须外置

这一条已经开始落地：

- Prompt 不允许长期写死在 use case 中。
- 模板必须从 `config/prompts/` 加载。
- 后续 Prompt A/B、不同语言版本、不同模型模板，应在配置层而非业务层切换。

### 11.4 Provider 创建必须收敛

这一条已经持续落地并已完成第一轮收口：

- 容器不应不断膨胀为 `if/else` 注册中心。
- Provider 创建逻辑应进入独立工厂或注册体系。
- 容器负责装配，不负责维护所有 Provider 细节。
- 当前已统一到工厂入口的 Provider 类型包括：
  - `embedding`
  - `llm`
  - `rerank`
  - `vision_llm` 边界

## 14. 模型接入设计规范

这一节用于指导后续所有模型接入开发，必须作为正式规格执行。

### 14.1 模型接入目标

本项目的模型接入不是“把一个 SDK 调起来”，而是要满足以下目标：

- 可替换
- 可配置
- 可测试
- 可降级
- 可观测

### 14.2 需要抽象的 Provider

- `EmbeddingProvider`
- `LlmProvider`
- `VisionLlmProvider`
- `RerankerProvider`
- 后续可选：`EvaluatorProvider`

### 14.3 抽象接口设计要求

接口必须满足：

- 输入输出结构稳定
- 与具体厂商 SDK 解耦
- 允许同步实现先落地，再根据需要演进异步接口

推荐设计方向：

- `EmbeddingProvider.embed_texts(texts: list[str]) -> list[list[float]]`
- `LlmProvider.generate(prompt: str, system_prompt: str | None, metadata: dict | None) -> str`
- `VisionLlmProvider.describe_image(image_path: str, prompt: str | None) -> VisionCaptionResult`
- `RerankerProvider.rerank(query: str, candidates: list[RetrievalResult], top_k: int) -> list[RetrievalResult]`

### 14.4 Provider 配置设计

配置层必须区分“业务配置”和“连接配置”。

当前建议的配置结构：

- `embedding.provider`
- `embedding.dimensions`
- `embedding_provider.api_base`
- `embedding_provider.api_key_env`
- `embedding_provider.model`
- `llm.provider`
- `llm.enabled`
- `llm.api_base`
- `llm.api_key_env`
- `llm.model`
- `vision_llm.provider`
- `vision_llm.enabled`
- `vision_llm.api_base`
- `vision_llm.api_key_env`
- `vision_llm.model`
- `rerank.provider`
- `rerank.enabled`
- `rerank.model`
- `rerank.api_base`
- `rerank.api_key_env`
- `prompts.answer_system_prompt_path`
- `prompts.answer_user_prompt_path`

### 14.5 敏感信息管理

必须遵循：

- `settings.yaml` 仅保存环境变量名，不保存真实密钥。
- 真实密钥从 `.env` 或系统环境变量读取。
- 所有 Provider 初始化时必须在日志中避免输出密钥原文。

### 14.6 默认 Provider 策略

为了保持项目可本地运行，必须保留占位或本地实现作为默认值：

- Embedding 默认：`hash`
- LLM 默认：`stub`
- Vision 默认：`disabled`
- Rerank 默认：`lexical`

当前项目状态补充：

- 测试与纯本地开发仍保留 `hash + stub` 路径。
- 当前项目配置文件已经接入一组真实 Provider 组合：
  - Embedding：`zhipu / embedding-3`
  - LLM：`deepseek / deepseek-chat`
- Provider 创建逻辑已开始迁移到独立工厂。
- 多模态骨架已落地，但 `Vision` 仍保持 `disabled` 默认值。

### 14.7 降级策略

模型调用必须具备明确降级策略：

- Embedding 失败：当前操作失败，不 silent fallback
- Rerank 失败：保留 fusion 结果并记录 trace
- LLM 生成失败：返回检索结果驱动的降级回答，不丢失 `sources`
- Vision 失败：跳过图像增强，但摄取主流程可继续

### 14.8 Trace 要求

所有真实模型调用都必须进入 trace：

- provider 名称
- model 名称
- 输入规模
- 输出规模
- elapsed_ms
- error 信息
- 是否触发 fallback

## 17. 回答生成与上下文组装策略

本项目必须坚持“检索”与“生成”分离建模。

只返回：

- Prompt 组装
- 上下文编号
- 调用 LLM
- 输出回答
- 引用来源映射

强制要求：

- 必须输出 `answer + sources`
- 不能隐藏检索依据

### 17.3 Prompt 组织要求

生成链路必须采用模板化设计：

- `system prompt` 与 `user prompt` 分离
- 模板从 `config/prompts/` 加载
- Prompt Builder 只做上下文拼装，不做业务决策
- 不允许把长期演进的 Prompt 文本写死在 use case 中

### 23.3 不继承的内容

- 参考项目中混乱的模块耦合方式
- Tool 内部承担全套初始化职责的写法
- 入口与业务编排混在一起的结构
- 边界不清的“core 大杂烩”

---

## 24. 开发与评审硬性规范

### 24.1 模块规范

- 每个模块只解决一类问题
- 不允许单文件承担过多职责
- 不允许为了“先跑通”长期保留脚本式耦合实现

### 24.2 代码规范

- 全量类型提示
- 核心接口先定义再实现
- 公共模型统一放置
- 异常类型分层定义

### 24.3 评审规范

提交代码必须回答清楚：

- 新增能力属于哪一层
- 对外接口是什么
- 是否引入新的耦合
- 是否可测试
- 是否影响 trace 与溯源

## 25. 结论

本项目后续建设方向已经明确：

- 功能能力上，参考 `MODULAR-RAG-MCP-SERVER-main` 的已验证主流业务链路。
- 工程结构上，不继承其混乱实现，而采用更严格的分层与模块化方式重建。
- 当前阶段上，检索评测 MVP、生成闭环基础版、真实模型接入、Prompt 外置和 Provider 工厂化已经落地。
- 当前结论上，项目未偏离主干，但文档优先级已做纠偏。
- 下一阶段上，重点不是继续堆功能，而是优先补“Dashboard 深度观测增强、摄取高级增强、Provider 收敛、多模态与高级评测”这些主干闭环，并继续完成 MCP legacy 兼容层退役与 SDK 收口。

截至 `2026-05-18` 的最终收口结论如下：

- 当前版本已经完成第一阶段封版，可进入维护与下一阶段迭代
- 主干业务链路已稳定：摄取、检索、回答、评测、MCP、REST、Dashboard 均可运行
- 架构方向未偏离参考项目目标：提取业务，不继承混乱结构
- 当前代码、测试、配置、文档口径已经基本一致
- 当前全量测试结果为 `56 passed`
- MCP 当前已完成“默认 SDK 入口 + 兼容层复用同一 SDK server”的第一阶段收口
- 本文档中列出的剩余闭环均已转入下一阶段优先事项，而非当前阶段阻塞项

本轮版本的剩余事项不再视为“本轮未完成工作”，而视为“下一阶段延期项”：

- 多模态真实处理链路
- 高级生成质量评测
- MCP legacy 兼容层退役与扩展能力收口
- 更深入的多集合与增量控制

后续所有开发工作都应围绕这三个问题判断是否合理：

1. 这项能力是否属于本项目明确范围。
2. 这项实现是否符合分层与可替换原则。
3. 这项改动是否让系统更接近“可持续开发完毕”，而不是更混乱。
