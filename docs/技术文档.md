## 2. 项目定位

`RAG-MCP` 是一个面向本地知识库与 AI Agent 集成场景的模块化 RAG 服务。

核心目标：

- 提供文档摄取、切分、向量化、索引、检索、重排、回答生成能力。
- 通过 MCP 协议向外部 AI Agent / MCP Client 暴露知识检索工具。
- 通过 REST API 与 Dashboard 提供本地管理、调试、验证与观测入口。
- 保持清晰的分层、可替换的 Provider 边界。

---

## 3. 非目标

当前项目明确不是：

- 通用多租户 AI 平台
- 完整业务后台系统
- 面向生产大规模集群的部署平台
- 已完成的多模态 RAG 系统
- 已完成的 LLM-as-Judge 评测平台

## 4. 当前架构总览

### 4.1 分层结构

```
Presentation
├── FastAPI REST API        (api/v1/routes.py)
├── MCP SDK Server          (mcp/sdk_server.py, mcp/tools.py)
└── Dashboard               (observability/dashboard/)

Application
├── handlers.py             (编排函数，trace 管理 + service 调用 + dict 输出)
└── factory.py              (RAGSystem + create_rag_system，装配入口)

Domain
├── Entities                (domain/entities/models.py)
├── Domain Services         (domain/services/)
└── Repository Contracts    (domain/repositories/contracts.py)

Infrastructure
├── Providers / Loaders / Splitters
├── Vector Stores / Sparse Index
├── Repositories / Pipeline
└── Prompt / Redis / Trace
```

### 4.2 装配方式

`factory.py` 中的 `create_rag_system()` 按依赖顺序直接创建所有组件并挂载到 `RAGSystem` 对象上：

1. 共享基础设施（trace、CollectionManager、Provider）
2. 摄取子系统（loader、splitter、pipeline）
3. 检索子系统（retrieval_service）
4. 生成子系统（answer_prompt_builder）

**不再有 Skill、Container、拓扑排序。** 依赖顺序由函数内书写顺序保证。

### 4.3 关键文件索引

| 文件 | 职责 |
|------|------|
| `factory.py` | RAGSystem 定义 + `create_rag_system()` + `get_rag()` 单例 |
| `application/handlers.py` | 16 个编排函数，每个 = trace + service + dict 输出 |
| `api/v1/routes.py` | REST 端点，直接调 handlers |
| `mcp/tools.py` | MCP 工具注册（3 个只读工具） |
| `mcp/sdk_server.py` | FastMCP 服务器构建 |
| `core/collection_manager.py` | 多 Collection 数据隔离 |
| `core/settings.py` | Pydantic 配置模型 |
| `infrastructure/providers/factories.py` | Provider 工厂 |

## 5. MCP 工具边界

MCP 渠道只暴露 **只读知识检索工具**，供外部 LLM 查询知识库后自己生成回答：

| 工具 | 用途 |
|------|------|
| `knowledge_search` | 检索知识库，返回相关文档块 |
| `list_documents` | 列出已摄取的文档 |
| `list_collections` | 列出可用的 Collection |

**管理操作**（ingest、delete、rebuild、evaluation）和 **回答生成**（generate_answer）走 REST API，不注册为 MCP 工具。

## 6. 对外入口

### 6.1 REST API

入口：`main.py`、`api/v1/routes.py`

端点：`/health`、`/ingest`、`/stats`、`/collections`、`/collections/rebuild`、`/query`、`/answers/generate`、`/answers/stream`、`/documents`、`/evaluations`、`/traces`

统一响应信封：`{"code": 0, "message": "ok", "data": {...}, "trace_id": "..."}`

Skill 门控通过 `_require_skill(name)` 直接读 `rag.settings.skills` 字段，不再经过 SkillRegistry。

### 6.2 MCP

入口：`mcp/sdk_server.py`、`mcp/tools.py`

支持三种传输：`stdio`、`streamable-http`、`sse`。工具注册由 `register_mcp_tools(server, rag)` 完成。

### 6.3 Dashboard

入口：`observability/dashboard/app.py`。6 个页面：Overview、Ingestion Manager、Answers、Documents、Traces、Evaluations。

## 7. 当前已实现能力

### 7.1 摄取与索引

- `txt`、`md`、`pdf`、`html`/`htm` 文档加载
- Confluence HTML 智能解析（HTMLParser + 噪声过滤 + 正则降级）
- 本地文件合法性校验（扩展名、大小、隐藏文件）
- 文本切块与边界优化（段落 → 句子 → 空白 → 强制切断）
- Embedding 写入（Zhipu / Hash）
- ChromaDB 向量索引 + SQLite FTS5 稀疏索引
- 文档与 chunk 元数据 JSON 持久化
- 基于文件内容变化的幂等摄取
- `force_rebuild` 替换式重建

### 7.2 检索

- Dense + Sparse 混合检索
- RRF 融合（`rrf_k=60`）
- Lexical Rerank
- Redis 检索缓存（可选）
- 统一 `results + sources + trace_id` 响应

### 7.3 生成式问答

- 基于检索结果构造 Prompt（外置模板 `answer_system.txt` / `answer_user.txt`）
- LLM 生成（OpenAI 兼容 `/chat/completions`）
- 同步 + SSE 流式双模式
- LLM 失败自动降级为检索结果拼接

### 7.4 文档管理

- 文档列表 / 摘要 / 详情 / 删除
- Collection 列表 / 重建
- 多 Collection 目录级数据隔离

### 7.5 可观测性

- ingestion / query / answer_generation / evaluation trace JSONL 持久化
- trace 列表与详情查询
- Dashboard 基础观测

### 7.6 评测

- Golden test set 加载
- HitRate@K + MRR
- 评测报告 JSONL 持久化

### 7.7 Provider 体系

- Embedding：Zhipu（生产）/ Hash（本地测试）/ Caching（Redis 装饰）
- LLM：`OpenAICompatibleLlmProvider`（DeepSeek / OpenAI / LiteLLM / vLLM 等）/ Stub（本地占位）
- Reranker：CrossEncoder（BAAI/bge-reranker-v2-m3）
- Vector Store：Chroma / Weaviate / Memory
- 全部通过 `settings.yaml` 切换

## 9. 数据与持久化边界

| 数据类型 | 格式 | 存储位置 |
|---------|------|---------|
| 文档/Chunk 元数据 | JSON | `{collection}/documents.json`, `chunks.json` |
| 向量 | ChromaDB (SQLite+HNSW) | `{collection}/chroma_live/` |
| BM25 索引 | SQLite FTS5 | `{collection}/bm25_fts.db` |
| Trace | JSONL | `data/traces/traces.jsonl` |
| 评测报告 | JSONL | `data/evaluations/reports.jsonl` |

Collection 隔离：`CollectionManager` 为每个 Collection 创建独立的 `CollectionScope`（包含 4 个后端），Pipeline 通过 `_ScopedStores` 上下文管理器临时切换。

## 10. 配置规范

### 10.1 三层架构

- Layer 1: Pydantic 模型默认值（`settings.py`）
- Layer 2: `config/settings.yaml`（覆盖默认值，入 Git）
- Layer 3: `.env`（敏感信息，不入 Git）

### 10.2 关键配置块

| 配置块 | 控制内容 |
|--------|---------|
| `embedding.provider` | `"zhipu"` / `"hash"` |
| `llm.provider` | `"deepseek"` / `"stub"` |
| `vector_store.provider` | `"chroma"` / `"weaviate"` / `"memory"` |
| `retrieval.*` | top_k / rrf_k / rerank 开关 |
| `skills.*` | 6 个子系统启停（REST 路由 + MCP 工具门控） |
| `mcp.transport` | `"stdio"` / `"streamable-http"` / `"sse"` |

## 11. 开发与扩展规则

### 11.1 总体原则

- 协议层薄，编排逻辑集中在 `handlers.py`
- 可替换性优先于厂商绑定（Provider 通过接口 + 工厂切换）
- 新增子系统在 `factory.py` 中新增 `_wire_xxx()` 函数

### 11.2 Provider 扩展

新增 Provider：
1. 写实现类（继承 `domain/repositories/contracts.py` 中的 ABC）
2. 在 `factories.py` 中加工厂函数并注册
3. 在 `settings.yaml` 中配置 `provider` 字段

### 11.3 新增 REST 端点

1. 在 `handlers.py` 中新增编排函数
2. 在 `routes.py` 中新增路由，调 handler
3. （可选）在 `SkillSettings` 中加门控字段

### 11.4 文档更新约束

出现以下变更时同步更新本文档：
- 新增或删除子系统
- 变更对外入口边界
- 变更默认 MCP 传输策略
- 变更存储方案
- 变更 Provider 配置结构

## 12. 结论

截至当前代码现状，`RAG-MCP` 已经形成：

- 基于 `factory.py` + `handlers.py` 的扁平架构（4 层，无 Skill/Container/UseCase）
- 同时支持 REST、MCP、Dashboard 三类入口
- 支持 `stdio / streamable-http / sse` 的 MCP 传输模式
- MCP 渠道仅暴露 3 个只读知识工具
- 具备摄取、检索、生成、管理、评测、观测六类核心能力
- 基于 `CollectionManager` 的多 Collection 数据隔离
- `OpenAICompatibleLlmProvider` 可接入任意 OpenAI 兼容 LLM 网关
- 支持 `txt`、`md`、`pdf`、`html`/`htm` 文档加载

同时应明确：

- 多模态仍是骨架
- 高级评测仍未完成
- 部署工程化仍未完成
