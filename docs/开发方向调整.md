## 2. 主方向定义

### 2.1 一句话

> 将 RAG-MCP 打造为一个**开源的、生产可用的、一键部署的 MCP 知识库服务**。开发者用 4 条命令即可从零到可用；团队用一条 `docker compose up` 即可部署企业级实例。

### 2.2 为什么选这个方向

原计划评估了 5 个落地方向。其中场景四（企业内网 Wiki 问答机器人）和场景五（MCP Server 开源发布）天然互补：

| | 只做场景四（企业部署） | 只做场景五（开源发布） |
|---|---|---|
| **优势** | 工程深度够，能展示架构能力 | 传播面广，社区可见 |
| **短板** | 只有你自己在用，没人知道 | 只有一个壳，缺乏生产级能力的说服力 |

两者结合产生质变：

```
开源产品化 = 企业级工程深度 × 社区可见度
           = "我写的工具别人真的在用" × "用的是一套生产级架构"
```

这一方向同时覆盖了其余三个场景：
- 场景一（Claude Desktop 本地问答）→ Phase 1 的验证动作
- 场景二（FastAPI 文档 Demo）→ Phase 2 的展示层
- 场景三（面试复习知识库）→ 推进过程中的个人使用与反馈来源

### 2.3 最终产品形态

```
用户视角的体验：

  $ pip install rag-mcp                    # 1. 安装
  $ rag-mcp init                           # 2. 生成配置
  $ rag-mcp ingest ./my-docs/              # 3. 摄入文档
  $ rag-mcp serve                          # 4. 启动服务

  4 条命令后，用户获得：
  - 一个运行在 http://127.0.0.1:8000 的 REST API
  - 一个运行在 http://127.0.0.1:9000/mcp 的 MCP 端点
  - 一个运行在 http://127.0.0.1:8501 的 Dashboard
  - 可以直接在 Claude Desktop / Cursor / Continue 中使用的 MCP 工具集

  团队用户额外执行：

  $ docker compose up                      # 5. 生产部署

  获得：
  - Weaviate 向量库（持久化、可扩展）
  - Redis 缓存（检索加速）
  - 多 Collection 隔离（不同项目/团队独立知识库）
  - API Key 认证
  - 完整的 Trace + Dashboard 观测
```

### 2.4 核心交付物清单

| 交付物 | 说明 | 面向谁 |
|--------|------|--------|
| `pip install rag-mcp` | PyPI 包，含 CLI 入口 | 所有用户 |
| `rag-mcp` CLI | `init / ingest / serve / eval` 子命令 | 开发者 |
| Docker Compose 方案 | 一键部署 Weaviate + Redis + RAG-MCP | 团队用户 |
| Quick Start 文档 | 5 分钟从零到首次查询 | 新用户 |

| 发布文章 | 技术博客 / V2EX / Reddit 发布帖 | 社区 |

## 3. 竞争定位

### 3.1 RAG 赛道玩家地图

```
                    代码侵入度
                    高 ←──────────────────────→ 低
                    （框架，需写代码）          （平台，开箱即用）

代码优先    ┌──────────────────┐  ┌──────────────────┐
（开发者    │ LangChain        │  │ RAG-MCP ◀ 我们的  │
  自己集成） │ LlamaIndex       │  │                  │
           │ Haystack         │  │ 定位：MCP 原生    │
           │ 特点：灵活但需要   │  │ 可部署的 RAG 服务 │
           │ 大量胶水代码       │  │                  │
           └──────────────────┘  └──────────────────┘

           ┌──────────────────┐  ┌──────────────────┐
低代码/    │ Dify             │  │ AnythingLLM      │
平台化     │ Flowise          │  │ ChatPDF          │
           │ 特点：拖拽式但    │  │ 特点：面向终端    │
           │ 定制化受限        │  │ 用户，不可编程    │
           └──────────────────┘  └──────────────────┘
                    高 ←──────────→ 低
                      面向人群的技术门槛
```

RAG-MCP 占据一个几乎空白的象限：**代码优先 + 可部署服务 + MCP 原生**。

### 3.2 竞争力对比

| 对比维度 | LangChain / LlamaIndex | Dify / Flowise | AnythingLLM | **RAG-MCP** |
|---------|------------------------|----------------|-------------|-------------|
| 形态 | Python 库 / 框架 | 低代码平台 | 桌面应用 | **可部署的 MCP 服务** |
| 使用方式 | `pip install` + 写胶水代码 | Web UI 拖拽 | GUI 操作 | **`pip install` + 4 条命令** |
| 给 AI Agent 用 | 需自己包 MCP Server | 不直接支持 | 不直接支持 | **原生 MCP 工具暴露** |
| 程序化控制 | ✅ 完全可控 | ❌ 受平台限制 | ❌ 基本不可编程 | **✅ REST + MCP 双协议** |
| 模块化 | 靠开发者自己拆分 | 平台定义的流程 | 无 | **6 个独立可启停的 Skill** |
| Provider 可替换 | ✅ 支持 | ⚠️ 部分 | ⚠️ 有限 | **✅ Embedding/LLM/VectorStore 三级可替换** |
| 混合检索 | 需手动组合 | ⚠️ 看平台实现 | ❌ 仅向量 | **✅ Dense+Sparse+RRF+Rerank 内置** |
| 部署难度 | 需自己写服务 | Docker | 桌面安装 | **CLI 一键 + Docker Compose** |

### 3.3 四个核心竞争力

**1. MCP 原生设计**
市面上多数 RAG 项目是先做 RAG、后补 MCP（或根本不做）。RAG-MCP 的 Skill 机制在架构层面就是为 MCP 工具暴露而设计的——每个 Skill 的 `register_tools()` 方法直接将 use case 转化为 MCP tool。这不是功能叠加，而是架构基因。

**2. 可部署性**
LangChain 和 LlamaIndex 是库，不是服务。开发者用它们做完 RAG 后，仍需自己写 FastAPI 包装、部署方案、观测系统。RAG-MCP 把这些"做完 RAG 之后还要做的事"全部内置。

**3. 模块化开关**
6 个 Skill 可按需启停。只需检索不需生成？关掉 `generation`。只需管理文档不需评测？关掉 `evaluation`。这种细粒度能力控制是单体 RAG 服务做不到的。

**4. 检索质量**
Dense + Sparse 混合检索 + RRF 融合 + Rerank 的组合，在检索质量上显著优于纯向量检索。作为开箱即用的内置能力，降低了用户获得高质量检索的门槛。

### 3.4 解决的场景与问题

| 场景 | 痛点 | RAG-MCP 如何解决 |
|------|------|------------------|
| 开发者在 Claude Desktop 中搜索自己的文档 | Claude 不知道你的本地文件内容 | MCP `stdio` 模式，Claude Desktop 直接调用 `knowledge_query` 工具 |
| 团队需要可编程的知识库 API | 低代码平台无法嵌入 CI/CD 或代码流程 | REST API + Python SDK 友好，可编程控制 |
| 需要快速切换 Embedding/LLM 供应商 | 大多数 RAG 方案绑定特定供应商 | Provider 三层抽象，改 yaml 即可切换 |
| 在 AI Agent 工作流中嵌入知识检索步骤 | LangChain 太灵活需写大量代码，Dify 太封闭无法嵌入 | MCP 工具可被任何 MCP Client 在 Agent 循环中调用 |
| 需要可观测的 RAG 系统 | 大部分自建 RAG 只有 print 日志 | JSONL Trace + Dashboard，每次检索/生成都有完整追踪 |
| 需要验证检索质量 | "搜得不准" 无法量化 | 内置评测框架 + Golden Test Set + HitRate/MRR 指标 |
| 小团队需要快速部署 | 不会配 K8s，也不想维护数据库 | CLI 一键启动（Chroma 嵌入式 + JSON 文件存储，零外部依赖） |

### 3.5 一句话定位

> 如果 LangChain 是 RAG 的"乐高积木"（灵活但需要自己搭），Dify 是 RAG 的"成品模型"（开箱即用但难以改装），那 RAG-MCP 就是 RAG 的**"可编程电器"**——插上电就能用，但每个接口都是标准化可编程的，且原生支持被 AI Agent 使用。

## 4. 与外部项目的标准集成

RAG-MCP 的设计原则之一是**通过标准协议集成，而非私有耦合**。本节定义它与外部项目（典型代表：Synapse AI Infra）的集成边界。

### 4.1 集成架构总览

```
                    ┌──────────────────────────────────┐
                    │          AI Agent / 业务应用        │
                    └──────────┬───────────┬───────────┘
                               │           │
              ┌────────────────┼───────────┼────────────────┐
              │                ▼           ▼                │
              │      ┌─────────────┐ ┌───────────┐         │
              │      │  MCP Tools  │ │ REST API  │         │
              │      │ (知识检索)   │ │           │         │
              │      └──────┬──────┘ └─────┬─────┘         │
              │             │              │                │
              │      ┌──────▼──────────────▼──────┐        │
              │      │        RAG-MCP             │        │  ← 知识层
              │      │  摄取→索引→检索→生成        │        │
              │      │  Skill 模块化 · MCP 协议    │        │
              │      └──────────────┬─────────────┘        │
              │                     │                       │
              │              调用 LLM 生成回答              │
              │              （OpenAI 兼容请求）            │
              │                     │                       │
              │      ┌──────────────▼─────────────┐        │
              │      │   外部 LLM 网关（可选）      │        │  ← 接入/治理层
              │      │   例：Synapse               │        │     (可替换)
              │      │   路由 · 审计 · 降级 · 计费  │        │
              │      └──────────────┬─────────────┘        │
              └─────────────────────┼───────────────────────┘
                                    │
                          ┌─────────▼─────────┐
                          │  LLM 供应商         │
                          │ (DeepSeek/OpenAI…) │
                          └───────────────────┘
```

### 4.2 两个集成方向

| 方向 | 协议 | 含义 |
|------|------|------|
| **外部 → RAG-MCP** | MCP / REST | AI Agent 或业务系统调用 RAG-MCP 的知识检索能力 |
| **RAG-MCP → 外部 LLM 网关** | OpenAI 兼容 `/chat/completions` | RAG-MCP 在生成回答时，把 LLM 请求发给一个可配置的 OpenAI 兼容端点（可以是 Synapse，也可以直连模型供应商） |

### 4.3 为什么这是工业标准做法

| 协议 | 工业标准属性 |
|------|-------------|
| OpenAI 兼容 `/v1/chat/completions` | 整个 LLM 工具链的默认方言。几乎所有框架都支持 `OPENAI_API_BASE` 覆盖。不是"我们约定的格式"，而是行业事实标准 |
| MCP (Model Context Protocol) | Anthropic 发布的开放协议，已被 Claude Desktop、Cursor、Continue 等主流 AI 工具原生支持 |
| REST `/api/v1/*` | 传统 HTTP 接口，适合 Web 应用和 Dashboard |

**关键结论**：两个项目不需要为对方做任何特殊适配。RAG-MCP 只需支持"把 LLM 请求发到一个可配置的 OpenAI 兼容端点"，外部网关只需做好"接收 OpenAI 格式请求并代理"。它们的串联是**两个标准的自然交汇**，而非两个项目的私有耦合。

### 4.4 可复用性的证明

```
RAG-MCP 通过配置 llm.api_base 接入不同目标：

  llm.api_base = "http://synapse:8000/v1"
    → 走 Synapse 网关（带审计/路由/降级/计费）

  llm.api_base = "https://api.deepseek.com"
    → 直连 DeepSeek（开发环境，跳过网关）

  llm.api_base = "https://api.openai.com/v1"
    → 直连 OpenAI（换模型供应商）

  llm.api_base = "https://any-other-gateway.com/v1"
    → 接入任何其他 OpenAI 兼容网关

外部 LLM 网关不感知调用方身份：

  请求带着 Authorization header 进来
  → 网关鉴权、审计、路由、转发
  → 调用方可能是 RAG-MCP、可能是业务系统、可能是 curl
  → 网关不关心，都是标准 OpenAI 格式请求
```

### 4.5 代码现状与待办

**已具备**（无需新增代码）：LLM Provider 已使用可配置的 `api_base` 并采用 OpenAI 兼容的 `/chat/completions` 格式（见 [deepseek_llm.py](../backend/src/rag_mcp/infrastructure/llm/deepseek_llm.py)）。切换网关只需修改 `settings.yaml` 中的 `llm.api_base`。

**待办**（见 Phase 3）：
- 验证端点 URL 拼接规范（当前为 `{api_base}/chat/completions`，需文档化 `api_base` 应包含 `/v1` 前缀）
- 在配置示例中提供"接入外部网关"的注释模板
- 验证 Synapse（或其他网关）返回的 OpenAI 格式响应能被正确解析

## 7. 简历叙事线（完成 Phase 4 后可用）

```
项目：RAG-MCP —— 开源 MCP 知识库服务

我独立设计并实现了一套面向 AI Agent 的知识检索系统，核心工作包括：

1. 架构设计
   - 六层分层架构（Presentation → Application → Domain → Infrastructure → Assembly）
   - 基于 SkillRegistry 的可插拔模块系统，6 个独立 Skill 覆盖知识库全生命周期
   - Provider 抽象层实现向量库/LLM/Embedding 的可替换切换

2. 协议实现
   - 基于 MCP 官方 SDK 实现 stdio / streamable-http / sse 三种传输模式
   - FastAPI REST API + MCP 双协议从统一容器装配，避免代码重复
   - LLM 调用采用 OpenAI 兼容协议，可接入任意标准 LLM 网关（如 Synapse）

3. 检索系统
   - Dense(Chroma/Weaviate) + Sparse(BM25) 混合检索 + RRF 融合 + Lexical Rerank
   - Embedding 缓存（Redis）降低 API 成本
```
