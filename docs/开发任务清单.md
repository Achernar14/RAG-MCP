## 1. 文档使用方式

本文档是 RAG-MCP 的**可执行任务清单**，将 [开发方向调整.md](开发方向调整.md) 中的 Phase 路线图拆解为原子任务。

**任务编号规则**：`P{阶段}-T{序号}`，如 `P1-T3` 表示 Phase 1 的第 3 个任务。

**每个任务包含**：
- 涉及文件（新增 / 修改）
- 依赖任务
- 验收标准
- 预估工作量（S=半天内 / M=1-2天 / L=3-5天）

**状态标记**：`[ ]` 待办 / `[~]` 进行中 / `[x]` 已完成

**优先级**：🔴 关键路径（阻塞后续）/ 🟡 重要 / 🟢 可选优化

**文档同步约束**：完成涉及架构或能力边界变更的任务后，必须同步更新 [技术文档.md](技术文档.md)。

## 5. Phase 3：生产级能力 + 标准集成（第 5-8 周）

**目标**：从"Demo"升级到"Production Ready"，验证标准集成边界。

### P3-T1 🔴 Weaviate 双模式支持（embedded + remote）

- **涉及文件**：修改 `backend/src/rag_mcp/infrastructure/vector_store/weaviate_store.py`、`backend/src/rag_mcp/core/settings.py`、`backend/src/rag_mcp/core/container.py`、`config/settings.yaml`、`config/settings.yaml.example`
- **依赖**：无
- **背景**：当前 `weaviate_store.py` 硬编码 `EmbeddedOptions`，而 Weaviate Embedded 不支持 Windows（见 weaviate/issues/3315）。这导致 Windows 用户无法使用 Weaviate，也阻塞了 P3-T6 的 Docker 化部署（容器化 Weaviate 必须以 remote 客户端方式连接，而非 embedded）。Phase 1 验证期间发现。
- **设计**：新增 `weaviate_mode` 配置字段，由它驱动两种连接路径：
  - `embedded`：现有 `EmbeddedOptions` 路径，Linux/macOS 本地开发用，Windows 不可用
  - `remote`：`weaviate.connect_to_local(host, port, grpc_port)` 或 `connect_to_custom()`，连接外部 Weaviate（Docker 容器 / Weaviate Cloud），全平台通用
- **验收标准**：
  - `weaviate_mode: remote` 可连接一个 Docker 容器化的 Weaviate 实例
  - `weaviate_mode: embedded` 在 Linux/macOS 保持现有行为
  - Windows 下 `weaviate_mode: remote` 端到端跑通（摄入 + 查询）
  - settings.yaml.example 提供两种模式的配置注释模板
  - 单元测试覆盖两种模式的连接构造逻辑（mock 实际连接）
- **配置示例**：
  ```yaml
  vector_store:
    provider: "weaviate"
    weaviate_mode: "embedded"      # "embedded" | "remote"
    weaviate_persistence_data_path: "data/vector_store/weaviate"
    weaviate_version: "1.37.2"
    # remote 模式专用（Docker / Cloud）
    weaviate_hostname: "127.0.0.1"
    weaviate_port: 8080
    weaviate_grpc_port: 50051
    weaviate_api_key: null
  ```
- **关于默认值**：本地开发默认配置**保持 Chroma**（不切 Weaviate Embedded），避免 Windows 用户开箱即崩。生产部署通过 docker-compose 走 Weaviate remote（见 P3-T6）。
- **工作量**：M

- **判断标准**：见[技术文档.md](技术文档.md) §12
- **重点**：`tests/integration/` 当前为空，Phase 2-3 应补充集成测试

### C-3 技术债务清理

- **已知债务**：
  - `mcp/tools/` 空目录（历史遗留，可删除）
  - `mcp/protocol.py` 与 `mcp/sdk_server.py` 存在重叠路径（需评估是否合并）
  - LLM Provider 类名 `DeepSeekLlmProvider` 但实际是通用 OpenAI 兼容实现（可重命名为 `OpenAICompatibleLlmProvider`）
  - **Weaviate Embedded 不支持 Windows**：[weaviate_store.py](../backend/src/rag_mcp/infrastructure/vector_store/weaviate_store.py) 硬编码 `EmbeddedOptions`，Windows 下无法启动。已立项为 P3-T1（Weaviate 双模式支持）正式修复——新增 `weaviate_mode: remote` 连接路径，本地开发默认保持 Chroma。Phase 1 验证期间发现
  - **测试套件在 Windows 下全部失败**：`tests/unit/*` 中约 10 个测试文件各自硬编码 `vector_store.provider: weaviate`，触发上述 Embedded 限制。修复方案：将测试 fixture 的 provider 改为 `memory` 或 `chroma`，并调整相关路径断言（部分测试用 `weaviate_persistence_data_path` 定位 bm25/chunks 文件，需同步改造）。**须在 P3-T7（CI/CD）之前解决**

## 10. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Weaviate Embedded 不支持 Windows | 阻塞 Windows 用户与 Docker 化部署 | P3-T1 实现 remote 模式；本地开发默认保持 Chroma |
| LLM API 成本超预期 | 影响 Demo 和测试 | P3-T2 启用 Redis 缓存；评测用小数据集 |
| MCP SDK 版本升级破坏兼容 | 阻塞 MCP 工具注册 | 锁定 `mcp[cli]` 版本，升级前跑全量测试 |
| PyPI 包名被占用 | 阻塞 P4-T3 | 提前在 PyPI 注册 `rag-mcp` 包名 |
| Collection 隔离改动范围大 | P3-T4 延期 | 优先保证单 Collection 稳定，多 Collection 作为 v0.3 目标 |
